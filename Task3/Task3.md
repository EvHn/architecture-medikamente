### Классификация данных и стратегия защиты

| Данные (Класс / Примеры) | В чем необходимость защиты |  Инструменты защиты (организационные и технические меры) |
| :----------------------- | :------------------------- | :------------------------------------------------------- |
| 1. Персональные данные пациентов <br> *(ФИО, дата рождения, адрес, телефон, паспортные данные, СНИЛС, полис ОМС)* | - Конфиденциальность: Прямая идентификация личности, риск кражи персональных данных, мошенничества.<br>- Законодательство: Требования 152-ФЗ (РФ), GDPR, HIPAA о защите ПДн и праве на забвение.<br>- Доступность: Критически важны для оказания медицинской помощи. | - Шифрование БД (Data-at-Rest): Прозрачное шифрование PostgreSQL/MySQL (TDE), шифрование файловой системы.<br>- Управление ключами (KMS): HashiCorp Vault, AWS KMS / Yandex KMS для хранения мастер-ключей.<br>- Маскирование данных: Автоматическое скрытие части номера документа на экране для непривилегированных пользователей (Dynamic Data Masking).<br>- RBAC: Доступ только для лечащего врача и ограниченного административного персонала. |
| 2. Медицинские данные (Особая категория) <br> (Диагнозы, результаты анализов, история болезни, генетические данные, снимки DICOM) | - Особый статус: Наиболее чувствительная категория. Утечка ведет к дискриминации, шантажу, нарушению врачебной тайны.<br>- Целостность: Искажение диагноза или результатов анализа создает прямую угрозу жизни и здоровью пациента.<br>- Юридические последствия: Уголовная ответственность за разглашение врачебной тайны. | - Сквозное шифрование при передаче: TLS 1.3 между микросервисами, обязательная проверка сертификатов.<br>- Электронная подпись (ЭЦП): Подписание врачом каждой записи в истории болезни для гарантии неизменности.<br>- Аудит доступа (SIEM): Логирование каждого факта просмотра/изменения медкарты с записью в защищенный WORM-журнал.<br>- DICOM TLS: Защищенный канал для передачи медицинских изображений. |
| 3. Данные интеграции с Лабораторией <br> (API-ключи, заказы на анализы в пути, результаты) | - Конфиденциальность трафика: Данные передаются за пределы контура клиники в публичную или VPN-сеть.<br>- Подмена результатов: Риск атаки "человек посередине" (MitM) с целью подмены результатов анализов для нанесения вреда. | - API Gateway c mTLS: Взаимная проверка сертификатов между шлюзом клиники и сервером лаборатории.<br>- Подпись запросов: Дополнительная целостность payload сообщения поверх TLS.<br>- Токенизация ID пациента: В запросах к лаборатории используется не ФИО и СНИЛС, а временный токен или внутренний ID эпизода лечения. |
| 4. Финансовые и бухгалтерские данные <br> (Счета, реестры на оплату, данные банковских карт / эквайринга, зарплатные ведомости) | - Финансовое мошенничество: Риск хищения средств клиники или пациентов.<br>- Стандарт PCI DSS: Если принимаются платежи картами, обязательное соблюдение требований по защите данных держателей карт.<br>- Налоговая отчетность: Целостность данных для ФНС. | - Токенизация платежных данных: Хранение не номера карты (PAN), а токена, выданного платежным шлюзом.<br>- Сегрегация сети: Выделение финансового отдела в отдельный VLAN с ограниченным доступом в интернет.<br>- DLP-система: Контроль передачи файлов с реквизитами за пределы корпоративной почты/мессенджеров. |
| 5. Данные учетных записей и аутентификации <br> (Логины, хеши паролей, сессионные токены JWT, ключи доступа к API) | - Критический актив: Компрометация УЗ врача или администратора ведет к полной потере контроля над всей медицинской информационной системой (МИС).<br>- Невозможность отказа (Non-repudiation): Каждое действие должно быть неоспоримо привязано к конкретному сотруднику. | - Многофакторная аутентификация: Обязательное использование OTP/TOTP или аппаратных ключей (YubiKey) для врачей и администраторов.<br>- Хранение хешей: Использование алгоритмов Argon2id или bcrypt.<br>- Короткое время жизни токенов: Ротация токенов и автоматическая инвалидация сессии при смене IP или бездействии. |
| 6. Обезличенные данные для ML-обучения <br> (Синтетические сеты, псевдонимизированные витрины данных) | - Риск реидентификации: Даже удалив ФИО, по набору редких диагнозов и возрасту можно восстановить личность.<br>- Защита интеллектуальной собственности: Модель ИИ и подготовленный датасет являются ценным активом клиники. | - Дифференциальная приватность (DP): Добавление калиброванного шума в обучающую выборку (Opacus, TensorFlow Privacy).<br>- Федеративное обучение: Обучение модели без выгрузки данных из клинического контура.<br>- Строгая изоляция контуров: Физическое или логическое отделение ML-среды (отдельный сегмент сети) от базы данных с ПДн. |
| 7. Аудиторские следы и системные журналы <br> (Логи действий пользователей, логи безопасности ОС, логи веб-сервера) | - Расследование инцидентов: В случае утечки необходимо точно знать, кто, когда и какие данные просматривал.<br>- Требования регуляторов. | - Централизованный сбор логов (SIEM): ELK Stack.<br>- WORM-хранилище (Write Once Read Many): Защита архивов логов от удаления и модификации администратором.<br>- Автоматизированные алерты: Срабатывание при попытке массовой выгрузки данных или доступе в нерабочее время. |
| 8. Конфигурации и секреты инфраструктуры <br> (Пароли БД, сертификаты TLS, переменные окружения, SSH-ключи, бэкапы) | - Горизонтальное перемещение атакующего: Утечка одного пароля от БД позволяет злоумышленнику скачать всю информацию.<br>- Доступность: Потеря ключей шифрования бэкапа равносильна полной потере данных. | - Хранение секретов : HashiCorp Vault, встроенные средства оркестратора контейнеров (Kubernetes Secrets).<br>- Автоматическая ротация сертификатов. |
